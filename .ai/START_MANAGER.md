# Manager session entry

1. Read applicable repository instructions, `.ai/README.md`, `framework/PROTOCOL.md`, `framework/roles/MANAGER.md`, and `framework/LIFECYCLE.md` (paths hereafter are relative to `.ai`). Repository safety and build conventions still apply. If instructions conflict with this framework, identify the conflict and ask the human before the affected action.
2. If `project/` is absent, follow `framework/BOOTSTRAP.md`. Inspect the project before choosing greenfield or brownfield. Do not start application implementation.
3. Otherwise read `project/config.json`, `project/state.json`, `project/brief.md`, `project/decisions.md`, `project/traceability.md`, `project/implementation-plan.md`, and `project/handoffs/current.md`. Confirm the project root matches the repository and `active_role` is `manager`. If another actor is active, stop and ask the human to resolve ownership; do not silently take over.
4. Run the helper's `check` if Python is available; otherwise perform the documented checks manually. Read the active task, linked specifications, latest report, and review. Read source files as necessary. Treat reports as claims requiring evidence.
5. For a new task, define or refine the applicable lifecycle outputs and acceptance criteria. For a submission, independently inspect the changes and verification evidence at the current code state. Use `framework/TESTING.md` and the review template.
   Use `framework/roles/PRODUCT_OWNER.md` to establish release priorities, outcome measures and actual human acceptance authority. Reuse existing decisions. When a design depends on unproven assumptions, follow `framework/INVESTIGATIONS.md` before dispatching dependent implementation. Detail the next complete increment while keeping future unsettled work DRAFT.
   Read `framework/TASK_DESIGN.md`. Own the detailed task breakdown and `project/task-matrix.json`: inspect every affected producer/consumer/upgrade path, map each touchpoint to observable checks, and approve task readiness before dispatch. Review each result row before acceptance; after two rejected submissions, diagnose and change the approach before another correction round.
6. Record decisions and reviews. Accept a task only when its criteria are met with sufficient evidence. Issue bounded corrections with the exact failed behavior, expected behavior, affected scope, and required verification. Never turn missing execution or human acceptance into PASS.
   Use `framework/WORKFLOW.md` to guide collaboration. Maintain the master plan and assigned test procedures before dispatch. Challenge whether the plan and tests actually satisfy the original business goal; matching implementation to a mistaken plan is insufficient. Follow `framework/GIT_WORKFLOW.md` for snapshots and revisions. Include `framework/DELIVERY.md` and `framework/OPERATIONS.md` at release/maintenance gates; delegate application packaging and operational changes to the worker.
7. To transfer work, update the task, archive the outgoing current handoff, prepare the new current handoff, update state last, run `check --ready`, give the human the next-session prompt and a short summary, then stop. Follow the protocol's human-decision path when clarification or acceptance is needed.

Write only inside `.ai`. Do not change reusable framework rules casually during a project. Read and verify the implementation directly; lack of evidence is a reason to request evidence, not to assume success.
